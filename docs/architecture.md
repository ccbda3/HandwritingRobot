# 系统架构

## 一句话

用少量个人笔迹样本学会书写风格，生成带真实书写时序的笔画轨迹，
经机械动力学约束优化后导出 GRBL G 代码，驱动写字机器人写出人眼难辨的字。

与现有方案的本质区别：传统写字软件只是描图片轮廓，**没有笔顺、没有时序**，写出来僵硬如机器描图。
本项目处理的是**联机笔迹**（笔尖坐标 + 笔序 + 时序 + 抬落笔 + 压感），复刻的是人的书写动作，不是字形轮廓。

## 语言分工（重要）

> 决策依据见 [ADR-0003](adr/0003-cpp-core-python-for-training.md)。
> 结论：**关键路径用 C++，训练与研究用 Python。不用纯 C。**

| 层 | 语言 | 职责 | 为什么 |
|---|---|---|---|
| `core/` | **C++17** | 轨迹数据结构、运动约束优化、G 代码生成、串口流式发送 | 交互式实时重算；发布版零 Python 依赖 |
| `app/` | **C++17 + Qt** | 桌面 UI、预览渲染 | 直接链接 `core`，无子进程、无序列化开销 |
| `src/handwriting/` | Python | 数据集分析、模型训练、实验与参数搜索 | PyTorch 生态只有 Python，CUDA kernel 库只服务 Python |
| `benchmarks/python/` | Python | 基线性能测量 | 为「是否移植到 C++」提供数据依据 |

### 为什么不用纯 C

Qt、ONNX Runtime、LibTorch、Eigen 全部是 C++ 接口。用纯 C 会把自己锁死在生态之外，
而且拿不到 RAII、`std::vector`、模板这些能显著降低出错率的工具。C++ 完全可以写成 C 风格。

### 为什么模型训练绝不能改用 C

PyTorch 的自动微分、CUDA kernel 库、优化器、数据加载器只服务 Python。
用 C 重写训练代码意味着放弃整个生态，几个月投入换来零收益——训练是离线批处理，
它慢一点只影响你的等待时间，不影响产品性能。

## 实测数据：语言选择到底值多少

`benchmarks/cpp/bench_pipeline.cpp` 与 `benchmarks/python/bench_pipeline.py` 使用完全相同的合成负载
（100 字 × 8 笔 × 60 点 = 48000 点），本机（MinGW g++ 15.2 / CPython 3.12）实测：

| 环节 | Python | C++ | 倍数 |
|---|---|---|---|
| 轨迹归一化 `fit_to_box` | 65.15 ms | 0.13 ms | **500×** |
| G 代码生成 | 65.67 ms | 37.42 ms | 1.8× |
| 计算合计 | 130.81 ms | 37.55 ms | 3.5× |
| 串口传输 49605 行 @ 380 行/秒 | 130.5 s | 130.5 s | 1× |
| 机床实际运行时间 | ~600 s | ~600 s | 1× |
| **计算占端到端耗时** | **0.018%** | **0.005%** | — |

**换语言把端到端从 730.8 秒降到 730.6 秒，提升 0.018%。**

结论有两条，都要记住：

1. **批处理吞吐不是选 C++ 的理由。** 瓶颈是串口带宽与机械运动，任何语言都改不了。
2. **交互延迟才是理由。** 用户拖动「抖动强度」滑块时需要实时重算整页预览：
   Python 的 65 ms 是 15 fps，手感发粘；C++ 的 0.13 ms 完全无感。
   桌面软件的胜负手是延迟，不是吞吐。

G 代码生成只快了 1.8 倍，因为两边都受限于数字转字符串。
C++ 侧已从 `ostringstream` 换成 `snprintf`（37 ms ← 63 ms），仍有优化空间。

## GRBL 的硬约束（决定优化算法的设计空间）

- 梯形速度规划 + junction deviation 拐角降速，**look-ahead 缓冲仅 16 段**
- **没有 S 曲线加加速度（jerk）限制** —— 这是机械振动的直接来源
- 串口 115200 baud ≈ 380 行/秒。0.1 mm 分段 + 30 mm/s 书写速度 = 300 段/秒，
  **正好卡在临界点上**，规划器饥饿会让纸面出现停顿点与墨点
- `G1 X Y Z F` 支持同块内三轴联动，因此**可以用 Z 值编码笔压变化**；
  但「Z 深度 → 实际笔压」是非线性的，需要标定表
- 抬落笔两种方案：Z 轴（连续可调，需弹簧笔）或主轴 PWM `M3/M5`（开关式，无法连续调压）

这些约束意味着**优化必须在 PC 端前置完成**，不能指望固件。
这正是本项目的学术切入点：现有笔迹生成模型只优化视觉真实度，不考虑机器人的动力学可执行性。
