# 0001. 采用架构决策记录

- 状态：已接受
- 日期：2026-10-14

## 背景

本项目跨越 C++ 桌面程序、Python 模型训练、GRBL 固件与机械硬件四个领域，
单人开发、周期长、上下文切换频繁。典型的失败模式是：三个月后忘了当初为什么这么设计，
于是推倒重来，或者在新约束下沿用已经失效的旧决策。

## 决策

在 `docs/adr/` 下用 Markdown 记录所有不可轻易逆转的架构决策。
每条 ADR 包含状态、背景、决策、理由、后果五部分，一经接受不再修改正文。

## 理由

- 决策的**理由**比决策本身更容易被遗忘。只记「用 C++」没用，要记「因为交互延迟要求 <1ms」，
  否则后来者（包括三个月后的自己）无法判断这条决策是否还成立。
- 写 ADR 的过程会强迫把「我觉得」变成「因为 X 所以 Y」，本身就是一次纠错。
- 纯文本、进版本库、可 diff，不需要额外工具。

## 后果

正面：决策可追溯；新人（或未来的自己）能快速理解现状的由来。

负面：每写一条 ADR 要花 20~30 分钟。因此只对返工成本超过一周的决策写 ADR，
日常实现细节写在代码注释里。
