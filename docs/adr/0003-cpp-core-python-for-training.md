# 0003. C++ 核心库 + Python 仅用于训练

- 状态：已接受
- 日期：2026-10-14
- 取代：早期「Qt 前端 + Python 子进程 + JSON 通信」方案

## 背景

项目需要同时满足两个目标：

1. **运行效率** —— 用户明确要求关键路径用 C，无关紧要的部分才用 Python。
2. **可训练** —— 笔迹风格模型需要小样本微调。

最初的方案是：Qt 前端用 C++，AI 推理放在独立 Python 子进程，通过 JSON 通信，
理由是「防止 UI 卡死、规避 C++ 嵌入 Python 的内存泄漏」。

这个方案有两个问题：一是没有量化验证「Python 慢到什么程度、慢在哪里」；
二是把 Python 运行时变成了**发布版的硬依赖**，安装包因此膨胀到 2~3 GB。

## 决策

1. **建立 C++ 核心库 `core/`**（C++17，不依赖 Qt、不依赖 Python），承载：
   轨迹数据结构、运动约束优化、G 代码生成、GRBL 串口流式发送。
   Qt 前端**直接链接**该库，不走子进程、不做序列化。
2. **Python 只用于训练与研究**：数据集分析、模型训练、实验与参数搜索、性能基线测量。
3. **推理走 C++ 侧**：Python 训练完成后导出 ONNX，由 C++ 加载（ONNX Runtime 或 LibTorch C++）。
   发布版**不含 Python 运行时**。
4. **不采用纯 C，采用 C++17。** Qt、ONNX Runtime、LibTorch、Eigen 全是 C++ 接口；
   C++ 完全可以写成 C 风格，但反过来拿不到 RAII、`std::vector`、模板这些降低出错率的工具。

## 理由

用相同的合成负载（100 字 × 8 笔 × 60 点 = 48000 点）实测，见 `benchmarks/`：

| 环节 | Python | C++ | 倍数 |
|---|---|---|---|
| 轨迹归一化 | 65.15 ms | 0.13 ms | 500× |
| G 代码生成 | 65.67 ms | 37.42 ms | 1.8× |
| 计算合计 | 130.81 ms | 37.55 ms | 3.5× |
| 串口传输 | 130.5 s | 130.5 s | 1× |
| 机床实际运行 | ~600 s | ~600 s | 1× |
| **计算占端到端** | **0.018%** | **0.005%** | — |

**换语言把端到端从 730.8 秒降到 730.6 秒，提升 0.018%。**
因此「C 比 Python 快所以端到端更快」这个理由**不成立**——瓶颈是串口带宽与机械运动。

真正的理由有三条：

1. **交互延迟。** 用户拖动「抖动强度」滑块时需要实时重算整页预览。
   Python 的 65 ms 是 15 fps，手感发粘；C++ 的 0.13 ms 无感。
   桌面软件的胜负手是延迟，不是吞吐。
2. **发布形态。** 无 Python 运行时意味着安装包从 2~3 GB 降到几十 MB，
   冷启动从数秒降到毫秒级，也不会因为用户环境里的 Python 版本冲突而失败。
3. **训练不能改 C。** PyTorch 的自动微分、CUDA kernel 库、优化器、数据加载器只服务 Python。
   用 C 重写训练代码等于放弃整个生态。训练是离线批处理，慢一点只影响等待时间。

## 后果

正面：发布版零 Python 依赖；交互延迟达标；核心库可被 Qt 前端与命令行工具共用；
`core/` 不依赖 Qt，可在 CI 中快速构建与测试。

负面：

- **双实现负担。** `core/`（C++）与 `src/handwriting/`（Python）目前各有一份轨迹与 G 代码实现。
  缓解：Python 侧定位为「研究用参考实现」，并在 `tests/` 中做行为对齐校验；
  若负担过重，引入 pybind11 让 Python 直接调用 C++，删除 Python 实现。
- 构建复杂度上升，开发者需要 C++ 工具链。
- ONNX 导出会引入量化误差，需要在验收阶段做数值比对。
