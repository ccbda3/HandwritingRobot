# 字形管线：文本 → 轨迹 → G 代码

阶段 1 的目标是**验证硬件链路**。这条链路不依赖任何 AI 模型，
因此可以先把机械精度、笔压一致性、串口时序这些真正的风险暴露出来。

```
文本
 │
 ├─ glyph.py     查标准笔顺库，取笔画中心线（medians）
 │               坐标：1024×1024 em 框，原点在基线，y 轴向上
 │
 ├─ render.py    坐标转换 → y 翻转、归一化到 0~1
 │               Catmull-Rom 样条平滑 + 按弧长重采样
 │               倾斜 / 抖动 / 笔压合成 / 时序合成
 │
 ├─ gcode.py     归一化轨迹 → 毫米版面 → GRBL G 代码
 │
 └─ preview.py   同一套版面 → SVG 预览（不动机器也能看到结果）
```

## 数据源

[hanzi-writer-data](https://github.com/chanind/hanzi-writer-data)（派生自
[Make Me a Hanzi](https://github.com/skishore/makemeahanzi)，最终来源是文鼎 PL 字体）。
每个字符一个 JSON，含 `strokes`（SVG 轮廓）与 `medians`（笔画中心线）。

**只用 `medians`。** 它自带正确的笔顺：数组顺序就是书写顺序。
这正是本项目相对「描图片轮廓」方案的核心区别 —— 传统工具只有轮廓，没有先后顺序。

完整字库的 `graphics.txt` 约 40 MB，超过 jsdelivr 的单文件限制，且
`raw.githubusercontent.com` 在部分网络下不可达。因此改为**按需下载单字 + 本地缓存**：

- 缓存目录默认 `.cache/glyphs`，已在 `.gitignore` 中排除
- 缓存文件名用 Unicode 码位（`U+6C38.json`）而非字符本身 ——
  Windows 上非 ASCII 文件名容易踩编码坑
- 下载带指数退避重试。CDN 偶发断连是常态，预取 150 字时几乎必然遇到
- `--offline` 只用缓存；`preload` 子命令可提前批量拉取

### 许可

数据派生自 Arphic PL 字体，**不随仓库分发**。详见
[ADR-0004](adr/0004-license-and-third-party-data.md)。

## 坐标系标定

Make Me a Hanzi 用 1024×1024 的 em 框，原点在基线、y 轴向上。
本管线统一转换到与采集器一致的坐标系：原点在方格左上角、y 轴向下、取值 0~1。

```
x_norm = (x_mmh - 0) / 1024
y_norm = (900 - y_mmh) / 1024
```

em 框取 `x ∈ [0, 1024]`、`y ∈ [-124, 900]`。这个范围不是拍脑袋定的，
用真实数据验证过（见 `tests/test_glyph.py::TestRealGlyphData`）：

| 字符 | 归一化后 | 应当的样子 |
|---|---|---|
| 口 | 约 22%~74% 见方 | 小字居中偏小 ✓ |
| 一 | 宽 > 0.5，高 < 0.15，位于 30%~70% 高度 | 横画在中线略上方 ✓ |
| 国、人 | 接近撑满 | 大字占满字格 ✓ |

**为什么不用「逐字包围盒归一化」**：那样「一」会被拉伸成贯穿整格的横线，
「口」会被放大到和「国」一样大，字格的视觉比例彻底失真。

## 平滑与重采样

`medians` 是稀疏折线（例如「永」的第一笔只有 4 个点），直接连线会有肉眼可见的折角。
管线做两步处理，**顺序不能颠倒**：

1. **Catmull-Rom 样条插值** —— 选它而不是 B 样条，因为它通过所有控制点。
   字形中心线的控制点本身落在笔画上，被平滑掉就意味着笔画走偏。
2. **按弧长重采样** —— 得到间距均匀的点序列。

若先重采样再平滑，控制点之间的直线段已经被固化，样条再平滑也救不回来
（`tests/test_curve.py` 用「拐点是否被摊开」验证了这个顺序）。

## 风格参数

当前阶段没有风格模型，只有四个可调参数在模拟书写差异：

| 参数 | 说明 |
|---|---|
| `slant_deg` | 字形倾斜，**右倾为正**。楷书 0~5°，行书可达 10° 以上 |
| `jitter` | 高斯抖动强度。建议 ≤ 0.005，0 为纯骨架 |
| `pressure_amplitude` | 提按幅度。长笔画两头重中间轻，点则单峰 |
| `writing_speed` | 合成时序用的书写速度 |

**这些参数不等于笔迹风格。** 真正的个人风格（笔画粗细分布、转折习惯、
连笔倾向）只能由风格模型从用户样本中学习。这里做的是让骨架跑通硬件链路，
并提供一个可对照的基线。

符号约定在两处使用，必须一致：`render.apply_slant` 与 `style.extract` 的
`slant_deg`。两边搞反的话，界面显示「右倾 10°」而实际输出是左倾，
这种错误肉眼很难发现 —— `tests/test_render.py::TestSlantAndStyleAgree` 专门防这一点。

## 用法

```bash
# 预取字形（需要联网；之后可离线使用）
python -m handwriting.cli preload "春眠不觉晓"

# 生成 G 代码 + SVG 预览
python -m handwriting.cli render "春眠不觉晓" -o chun.nc --svg chun.svg \
    --chars-per-line 10 --char-size 20 --slant 3

# 只看统计不写文件
python -m handwriting.cli render "永" --dry-run

# 用主轴 PWM 控制抬落笔（舵机 / 电磁铁方案）
python -m handwriting.cli render "永" -o yong.nc --spindle
```

CLI 会打印**串口传输时间**估算。这是整条链路的真实瓶颈：
GRBL @ 115200 baud 约 380 行/秒，而计算只占端到端耗时的 0.02%
（见 [architecture.md](architecture.md)）。

## 已知限制

- **笔压是合成的，不是学来的。** 字形数据没有压感。当前的提按曲线按楷书规律
  生成，但真正的提按取决于笔画类型（撇要收细、捺要放粗），
  而字形数据只给中心线、不给笔画类型。等风格模型接入后由模型直接生成。
- **时序是合成的。** 同理，真实时序必须来自风格模型。
- **抖动不等于风格。** 见上文。
- **未做机器运动约束优化。** 当前是「每个采样点一条 G1」，分段密度只由
  `resample_step` 决定。GRBL 的梯形速度规划与 16 段 look-ahead 缓冲
  会对密集分段产生停顿，这属于阶段 4 的优化内容，也是论文的核心。
- **尚未实测。** 目前只验证了 G 代码与 SVG 在几何上正确，
  还没有真正驱动过写字机。
